1.1.0.7 里修的是两处**代码级**的确定性 bug，感谢 @MuttonIsHere 的持续跟踪，也感谢 @qiantaiduo7-lgtm 的复测：

- `AudioSpectrumCapture` 里「新样本计数」用错了变量（达到 FFT 窗长后就不再增长），导致 FFT 一辈子只跑一次，频谱画出来就永远静止；
- 取窗索引错位一轮，窗内一半样本是无效的 0，表现为幅度极低甚至完全不跳。

但上面这两条只解释「柱条不动」，解释不了「一根柱条都没有」。所以我重新读了这一整条链路，又定位到一个**必现的挂载缺陷**，这次一并修了：

- 底纹宿主（每一行主界面里承载底纹的那层）是带缓存的，而**宿主的内容和纹理类型是强绑定的**：静态纹理用背景画刷、动态频谱挂 `SpectrumTextureOverlay` 子项、Aero 挂条纹子项。旧代码在「宿主已存在」时直接复用，不校验类型 —— 于是**从别的纹理切到动态频谱时，宿主还是旧的，频谱覆盖层永远挂不上去**，画面上就是彻底空白。分体主界面下的切换路径尤其容易踩中。现在宿主会记录自己创建时的纹理类型，类型不符就重建，切换纹理后频谱一定能挂上。

要抓的关键行（每 10 秒会打一次，日志不会刷屏）：

- `频谱捕获: 启动成功。设备采样率=... 声道=...` —— 回环有没有起来；
- `频谱捕获: 默认输出设备="..." 已静音/未静音 主音量=...%` —— **回环抓的是「默认输出设备」，不是「正在出声的设备」**。如果你实际在听的是蓝牙耳机 / USB 声卡 / HDMI，而在 Windows 里没把它们设为默认输出设备，回环抓到的就是纯静音，一根柱条都不会画出来。你机器上的「SMTC 一切正常」不能排除这种情况，因为 SMTC 和音频设备完全无关；
- `频谱捕获: 收到首批音频数据。...` —— 回环真的在送数据；
- `频谱捕获: 首次得到有效电平（最大=...）` —— 出现这一行就说明捕获 → FFT → 电平这条链路完全正常，问题在渲染侧；
- `频谱运行: ... 判定=...` —— 这行会直接给结论，对照着看就行：

| 判定 | 含义 |
| --- | --- |
| 回环完全没送数据 | 默认输出设备不可用 / 被独占 |
| 回环未送新样本 | 捕获被中断（切设备、音频服务重启），插件会自动重建 |
| 有样本但全为静音 | 实际出声设备不是默认输出设备（最常见） |
| 正常（捕获到有效电平） | 捕获链路没问题，若仍看不到柱条请告诉我，那就是渲染侧的事 |
| 未挂接任何覆盖层 | 宿主没建立，这种现在应该已经修掉了 |
