## 「点渲染并应用 → 卡死 → 静默崩溃」= 解码器释放竞态

### 定性（不是猜的）

事件日志（`wevtutil qe Application /q:"*[System[Provider[@Name='.NET Runtime']]]"`，
沙箱里 `Get-WinEvent` 被拒但 wevtutil 可用）给出确切栈，时间与用户操作吻合：

```
Date: 2026-09-28T18:21:49  Event ID 1026
Exception Info: System.AccessViolationException: Attempted to read or write protected memory.
   at ClassIslandInjector.FFmpegVideoDecoder.ReadFrame(Byte[] ByRef)
   at ClassIslandInjector.VideoFrameSource.TryReadFrame(...)
   at ClassIslandInjector.VideoProjectPlayer.PumpTrack(TrackState, Double)
   at ClassIslandInjector.VideoProjectPlayer.Loop()
```

对照 `video-editor.log`：最后一条是 18:21:48 的预览帧日志、**没有** `渲染开始` 行
→ 说明死在 `RenderAndApply` 的第一步 `StopPreview()`，即 `VideoProjectPlayer.Dispose()`。

### 根因：Dispose 与解码线程没有互斥，且顺序反了

- `VideoProjectPlayer.Dispose()` 旧实现：先 `state.Source?.Dispose()`（直接 free native
  上下文）**再** `_worker?.Join(800)`。播放线程此刻多半正卡在 `ReadFrame` 里 → 继续读已释放的
  `AVCodecContext`/`SwsContext` → AV。`AccessViolationException` 默认抓不住，进程直接死
  （`Application Error`：模块 `coreclr.dll`、`0xc0000005`）→ 用户看到的「卡死 + 静默崩溃」。
- 这也是 `RenderAndApply` 里那句注释（"三路并发……容易踩到解码器释放竞态"）预言过的坑。

### 修法（两层）

1. `FFmpegVideoDecoder` 加互斥门 `_gate` + `_disposed`：`ReadFrame` / `SeekTo` / `Restart`
   全部走 `RunGated(...)`，`Dispose` 在门内释放（幂等）→ **在途帧读完之前不会 free**。
2. `VideoProjectPlayer.Dispose` 改成「先 `Consumed.Set()` 叫醒等待 → `Join(3000)` → 退出才释放
   解码器」；线程 3s 没退就不动解码器，交给线程自己在 `Loop` 退出路径释放（`_disposed` 判定）。

### 验证（可复现，已进仓库当回归）

临时探针用 `git show HEAD:FFmpegVideoDecoder.cs` 生成「旧版」副本做 A/B：

| | 结果 |
|---|---|
| 旧版 | `System.AccessViolationException … sws_scale → FFmpegVideoDecoderOld.ReadFrame` → SIGSEGV（退出码 139） |
| 新版 | Dispose 阻塞 ~110ms 等在途帧、读线程自然退出、释放后再读返回 false、进程存活 |

已固化为 `tools\RaceProbe`（5 轮「解码中释放」断言，退出码 0 = 安全），并写进 `agents.md` 探针清单。

**给未来的自己**：FFmpeg native 上下文（`AVCodecContext`/`SwsContext`/`AVFormatContext`）的
释放规则 = ①先停线程并 Join、②释放前与所有可能正在用它 native 调用的入口互斥。
`VideoFrameSource` / `MfVideoFrameSource` 各自 Join 自己线程的顺序是对的，出问题的是**持有者**
（播放器）在另外的线程上释放它们。

## 片段时间轴变速（Speed）+ 可选是否变调

### 模型

- `VideoClip.Speed`（0.1..8，默认 1）、`PreservePitch`（默认 false = 变速同时变调）。
- `Duration` 由 `OutPoint-InPoint` 改为 `(OutPoint-InPoint)/EffectiveSpeed` → 时间轴宽度、落位、
  `AudioGainAt` 的淡入淡出时长全部自动跟着变；入出点（素材位置）不动。
- 新增 `SourceTimeAt(localTime) = InPoint + localTime*速度`，替换所有「时间轴时间 → 素材时间」的换算：
  `VideoProjectPlayer`（三条路径）、`VideoProjectRenderer`、编辑器舞台取帧、混音器的 expectedSource。
- `ApplyTrim` 左头：时间轴位移要按速度折算（否则右缘漂移）。

### 音频：AudioSpeedReader（新文件，与 UI 无关，可单独测）

- 原速且不变调 → 直接透传（零开销）。
- 变调 → 线性插值重采样（最省 CPU）。
- 保持音调 → SOLA（30ms 窗 / 15ms 跳 / ±1ms 相关搜索，左声道隔点取样）。
  **关键**：相邻输出窗重叠 15ms，重叠段要能回改「已产出但未交付」的尾部 → 输出缓冲始终扣住
  最后 15ms（15ms 额外延迟，无感）。
- `SourceFramesConsumed` 必须报**已交付帧 × 速度**，不能报分析窗口位置：SOLA 会提前读满一窗，
  报分析位置会让调用方以为音频跑在前面 → 混音器每块都触发重定位（听感断续）。
  这一点是探针测出来的（报分析位置时 1s 输出报成消耗 2.28s）。
- 混音器 `AudioSource` 挂一个 reader；`ReadFrames`（旧的裸计数）改为只读属性转发 reader 的记账。

### 验证（探针，数值断言）

`--speed`：喂 1kHz 正弦，量输出频率与长度。

| 用例 | 输出 | 消耗素材 | 频率 |
|---|---|---|---|
| 2.0× 变调 | 1s | 2s | 2000Hz |
| 2.0× 保持音调 | 1s | 2s | **1000Hz** |
| 0.5× 保持音调 | 1s | 0.5s | 1000Hz |
| 1.5× 变调 | 1s | 1.5s | 1500Hz |
| 1.0× 原速 | 1s | 1s | 1000Hz |

### 已知限制

渲染（`VideoProjectRenderer`）**只出视频、不混音**（FFmpegVideoEncoder 无音频轨），
所以渲染产物的声音取不到 —— 变速对渲染只影响画面。

## 编辑器交互：空格键 + 定格

### 空格只切预览播放

- 原因：快捷键原来挂在**冒泡**阶段的窗口 KeyDown 上，而焦点在按钮/开关/下拉时，
  控件会先吃掉空格（Button → Click、ToggleSwitch → 切换），于是"空格看焦点行事"。
- 修法：`AddHandler(KeyDownEvent, ..., RoutingStrategies.Tunnel)` —— 隧道阶段先于控件，标 Handled 后
  控件拿不到。唯一例外是用户正在打字：`IsKeyboardInputFocused()` 沿可视树上溯，
  命中 TextBox / AutoCompleteBox（字体下拉的编辑框）/ ContentDialog 时全部放行。
  （数字框内部是 TextBox，点进去打字也被正确放行；ComboBox 不再用空格展开 —— 这是有意的取舍。）

### 定格（时间轴工具条，画幅按钮之后）

- 仅选中视频片段时启用（`Kind == "Video"` 且有 SourcePath）。
- 取帧：按片段速度把播放头换算成素材时间 `SourceTimeAt()`，播放头在片段外则夹到最近画面
  （状态栏说明）；用 `VideoFrameSource`（长边上限 1920）解一帧 → 写 PNG 到
  `配置目录/frames/<素材名>_<时间>s_<时分秒毫秒>.png` → 图片片段放**最上方新轨道**
  （同轨会与原视频重叠而被自动挪位）+ 复制原片段的全部变换/裁切/灰度/翻转 → 构图与视频一致。
  同时把 PNG 加进素材库（以后能直接拖回时间轴）。
- ⚠️ 存图必须裁到**逻辑尺寸**：解码输出被 16 对齐补过行/列（1280x578 → 帧缓冲 1280x592），
  直接整帧存图会让定格图底部多一条边条。`LogicalFrameSize()` 按解码器的缩放口径复算真实尺寸。
- 验证（探针 `--frame`）：解码 → 按同款写法存 PNG → 读回**逐像素比对 0 处不一致**，
  尺寸 1280x578（已裁掉 592 的填充行）。

## 低配机器体验：性能 + 触摸适配

### 先测数据（不猜）

`--bench`（1080p 源逐帧解码，本机 4 逻辑核）：

| maxDimension | ms/帧 | 上限 fps |
|---|---|---|
| 320 | 11.4 | 88 |
| 480 | 10.0 | 100 |
| 640 | 9.3 | 107 |
| 800 | 12.0 | 83 |
| 1280 | 13.1 | 76 |

结论：**解码本身不是瓶颈**（24fps 只要 ~0.3 核）。卡顿更像「多路并发 + 每帧重绘」：
编辑器预览 + 主界面底图同时全尺寸解码 + 两处贴图，再加 Avalonia 每帧重绘整窗口。

### 三项针对性措施

1. **预览画质自适应**（`AdaptPreviewQuality`）：在 UI 线程的帧回调里测「拿到并贴完图」的真实帧率
   （取有帧产出的轨道里最慢的一条；比只测解码更贴近体感），每 2s 评估一次：
   低于目标 60% 就降档（800/24 → 640/24 → 480/20 → 400/16），高于 95% 且已过了 12s 冷却才升档。
   降档 3s 冷却、升档 12s 冷却 + 换档后清空统计窗口（避免把重建那一下算成掉帧）。
   换档会重建播放器（参数在构造时固定），但沿用当前播放头，无明显跳变；状态栏提示一次。
2. **音画漂移校正**（`VideoProjectPlayer.CheckAudioSync`）：视频走系统墙钟、音频走声卡采样时钟，
   0.1% 的偏差在 266s 时间轴上就是 0.27s。每 5s 比一次 `ProjectAudioMixer.AudibleTime`
   （用 NAudio `IWavePosition.GetPosition()` 拿**声卡真实播放位置**，而不是"已渲染帧数"——
   后者领先一个 WASAPI 缓冲 ~150ms，拿它比会一直误判）与墙钟，超 0.15s 就把音频重定位。
3. **编辑器打开期间挂起主界面底图**（`InjectorRuntime.SuspendBackgroundPlayback`）：
   单文件底图走 `VideoFrameSource.SetSuspended`（解码线程 sleep，保留位置），
   工程底图走播放器 `Pause()/Resume()`。关编辑器或应用渲染后恢复。

### 触摸适配

- **点按素材卡片直接加到播放头**（`AddAssetAtPlayhead`）：触摸屏上 OLE 拖拽不可用，
  点按是唯一可靠路径；鼠标行为不变（点按仍只是选中）。列表视图用双击/双击点按。
- 拖拽入口（`StartAssetDrag`、封面卡 PointerMoved）只对鼠标生效，把手指滑动留给滚动。
- 点击目标放大：时间轴工具条按钮 28→36(高 34)、播放/全屏 32→40(高 36)、
  轨道头按钮 28x24→34x28、裁剪手柄命中区 18→26、工具下拉 138×?→150(高 34)。
  舞台缩放/旋转手柄本来就是 24px 命中区，够用。

## 「渲染带音频」代价评估（只评估，未实现）

### 能力核查（探针 `--aac`）：链路齐全，零新增依赖

- 原生 `aac` 编码器**可用**，支持 `AV_SAMPLE_FMT_FLTP` + 48000Hz；mp4 复用器默认音频编码就是 AAC。
- `swresample` **已在 `FFmpegRuntime.RequiredLibraryNames` 里**（音频解码器本来就在用它做 s16 重采样），
  所以带音频渲染**不需要多下发任何 dll**。
- 现有音频输出格式：48kHz / 2ch / s16（`FFmpegAudioDecoder.OutSampleRate` 等常量）。

### 运行时代价（探针 `--mixbench`，本机 4 逻辑核，实测）

| 环节 | 每「输出分钟」CPU |
|---|---|
| 音频解码（44.1k mp3→48k s16）+ 混合 + 每帧增益 | 282ms（≈213× 实时） |
| AAC 128kbps 编码 | 525ms（≈114× 实时） |
| **音频合计** | **≈0.8s** |

对照视频侧（x264 veryfast，30fps）：224×40 → 4.35s/min；640×360 → 8.2s/min；
1280×720 → 66.6s/min。再加视频解码（9~13ms/帧 ≈ 21.6s/min）与逐像素合成。

⇒ **音频占比：720p 约 1~3%，极小画幅（224×40）约 18%**；绝对量都是「每输出分钟不到 1 秒」。
CRF 低时预设升到 `medium`，视频更慢，音频占比进一步降到 <1%。

### 实现工作量（约 500 行）

1. `FFmpegVideoEncoder` 扩展为视频+音频双流：第二个 `AVStream`/`AVCodecContext`/`AVFrame(fltp)`/
   `AVPacket`，`_tbStream` 要拆成每流一份；`SwrContext`（s16 interleaved → fltp planar）；
   `EncodeAudio(pcm, frames)`；`Finish()` 要 flush 音频编码器（≈150 行）。
2. 离线混音：现有 `ProjectAudioMixer` 绑死在 NAudio 实时回调（`MixProvider.Read`/`AudibleTime`/
   漂移校正）上，离线要抽一条路径或新写 `OfflineAudioMixer`，复用已验证的
   `AudioSource.TryCreate` + `AudioSpeedReader`（变速/变调）+ `VideoClip.AudioGainAt` +
   `ProjectAudioMixer.TrackGainOf`（≈200~250 行，风险集中在这里）。
3. `VideoProjectRenderer` 按输出帧喂音频：`endSample = round((frame+1)/fps * 48000)`，
   用「样本号游标」而非浮点累加（非整数帧率也不漂）；处理片段中途开始/结束（≈40 行）。
4. 渲染选项加「包含音频」勾选；验证探针（双流/时长/变速不变调）约 120 行。

### 风险与结论

- 唯一诡异点：AAC 编码器有 ~1024 样本（≈21ms）前置延迟，mp4 复用器**会自己写 edit list 补偿**；
  自己拼时间戳时才需要处理 `AV_PKT_DATA_SKIP_SAMPLES`。
- **重要发现：带不带音频对本体功能没影响。** `ApplyRenderedVideo` 把产物写进
  `Settings.VideoFillPath` 当主界面底图，而底图那条链路（`VideoFrameSource`）只解视频流、
  不碰音频 —— 音频纯粹是给「导出的成片拿去别的播放器看」用的，代价是文件大 128kbps ≈ 1MB/分钟。
  ⇒ 应做成勾选项（建议默认不带）。

## 渲染带音频 + 主界面底图放声（完整链路）

需求：「别人希望 ClassIsland 能播放带声音的视频」→ 不只是导出带音频，**主界面底图也要出声**。

### 现状盘点（避免重复造轮子）

- 单文件底图的音频播放**早就有了**：`VideoAudioPlayer`（FFmpeg 解音频轨 + swr → 48k/2ch/s16 →
  NAudio `WasapiOut` 共享模式，拉模型）+ `MainWindowStyleInjector.ApplyVideoAudio/StopVideoAudio`
  + 设置项 `VideoFillAudioEnabled` / `VideoFillAudioVolume`（设置页已有开关）。
- 工程（多片段）背景的音频也早就有了：`VideoProjectPlayer` + `ProjectAudioMixer`。
- **真正缺的只有一块：编辑器「渲染并应用」产出的 mp4 没有音轨** → 底图没声音可放。

### 实现

1. `FFmpegVideoEncoder` 加第二条 AAC 流（原生 `aac` + `SwrContext` s16 交错 → fltp 平面；
   `swresample` 早在必需库清单里，**不需要多下发 dll**）。`EncodeAudio(pcm, frames)` 内部按
   AAC frame_size(1024) 攒帧；`Finish()` 两路都 flush（音频尾巴补静音凑满一帧）。
2. `ProjectAudioMixer.StartOffline(project)` + `ReadForRender(buffer, offset, count)`：
   不建 WASAPI 输出，复用同一个 `MixChunk` → 渲染与预览声音口径一致（含变速/保持音调/轨静音）。
3. `VideoProjectRenderer`：每输出帧按 `endSample = round((k+1)/fps × 48000)` 取音频区间
   （**累计样本号**，非整数帧率也不漂），工程无可出声内容时跳过并提示。
4. 渲染选项加「包含音频」（`InjectorSettings.RenderIncludeAudio`，默认开，记住偏好）；
   应用带音频的产物时顺手打开 `VideoFillAudioEnabled`（否则用户以为没声音）。
5. 底图循环同步：`VideoFrameSource.OnLoopRestart` → 音频 `Seek(0)`；「播放声音」开启时
   底图按**源帧率**播放（否则视频循环周期 ≠ 音频时长，一个循环里音频重复若干遍）。

### ⚠️ 踩到的坑（价值最高的一条）

**`avcodec_receive_packet` 不设置 `pkt->stream_index`（默认 0）。** 单流（纯视频）时
视频恰好就是 0 号流，所以永远看不出问题；一加音轨，音频包被当视频包塞进 0 号流 →
复用器刷 `Application provided invalid, non monotonically increasing dts to muxer in stream 0`，
视频轨被写坏：**产物只剩 1369 字节**、`Could not find codec parameters for stream 0 ... unspecified
pixel format`、再读它还会在 `libswscale/swscale_internal.h:773` 断言崩掉。
修法：`DrainPackets(ctx, pkt, tb, streamIndex)` 按所属流显式赋值。
另外给编码器加了可选 `Trace` 钩子（默认关闭）—— 复用器的时间戳问题在 FFmpeg 自己的 log 里
只露一行，打开它才能看到「谁在什么时候送了哪个时间戳」。**是这个钩子找到的根因，不是猜的。**

### 验证

`tools\RaceProbe --audio [视频] [FFmpeg库目录] [输出目录]`（探针自合成 1kHz 正弦当音源，
跑真实 `VideoProjectRenderer` 后从 mp4 解回音频量化）：

| 用例 | 产物时长 | 片段前静音 | 段内 RMS | 频率 |
|---|---|---|---|---|
| 2× 保持音调 | 2.517s（期望 2.5） | 0.0000 | 0.354 | **999Hz**（不变调）|
| 2× 变调 | 2.517s | 0.0000 | 0.353 | **1999Hz** |
| 1× 原速 | 2.517s | 0.0000 | 0.354 | 1000Hz |
| 0.5× 保持音调 | 4.501s（期望 4.5） | 0.0000 | 0.354 | **1000Hz** |
| 关闭「包含音频」| 无音轨 ✓ | — | — | — |

顺带确认一个**既有**（与音轨无关）的行为：`FFmpegVideoDecoder` 不在 EOF 冲解码器，
B 帧重排缓冲里最后 2 帧读不出来（25 帧的文件解出 23 帧、关音轨也一样）。
今天没动它（属解码器核心路径，改动风险大）；要修就在 EOF 时 `send_frame(NULL)` 再 drain。

## 预览卡顿 / 音画不同步：自己上压力测出来的 3 个真 bug

用户让我「自己上点压力试试」（边预览边 seek、调倍速、开浏览器）。宿主的 GUI 在另一个桌面会话，
看不到画面 —— 所以改成**量化测量**：写了压力探针 `RaceProbe --stress`，跑真实的
`VideoProjectPlayer`，把「卡顿」量成「每轨投递帧率 / 最大间隔」，把「不同步」量成「声卡位置 vs 渲染位置偏差」。

### 关键建模（第一版探针写错的地方）

**UI 的代价必须放在另一条线程**（真实链路：播放线程 Post → UI 线程拷贝+重绘 → 播放线程等 Consumed）。
第一版把忙等压在播放线程里 → 等于测错东西，所有数字都失真。

### 前置数据（本机 4 核，手机视频 1280x578 / **54.2fps**）

- 顺序解一帧（解到 800px）：**9.7ms**；随机 seek+解一帧：**57ms**（最大 84ms）。
- 源 54fps、显示 24fps ⇒ 每轨每秒要解码 54 帧扔掉 30 帧 = 0.63 核/轨，而**解码全在一线程串行**。

### 3 个真 bug（都修了）

1. **消费信号会丢 → 画面永久卡住（最致命）**
   `PumpTrack` 里顺序是 `_onFrame(...)` → `Consumed.Reset()`。UI 线程可能在 `_onFrame` 返回**之前**
   就消费完并 `MarkTrackConsumed`（Set），随后那句 Reset 把信号抹掉 → 此后 `!Consumed.IsSet` 恒成立
   → 该轨**永久不再投递**。实测：8 秒只投递 6 帧（修复后 139 帧）。日志特征：
   `显6 丢15 seek0[等UI消化]` 三个计数长时间完全冻结。
   修法：**先 Reset 再回调**（视频与覆盖层两条分支都要）。
2. **追赶无上限 → 解码丢弃把整拍吃光**
   落后 > 48 帧才跳、且一次硬解 32 帧（371ms）；多轨串行时单拍涨到 1.1s，投递率崩到 1fps。
   修法：`CatchUpSeekFrames = 8`（落后 0.33s 就 seek：57ms ≪ 371ms）+ `MaxSkipPerTick = 4`。
3. **`AudibleTime` 把声卡累计位置当绝对时间 → 漂移校正喂假数据**
   `WasapiOut.GetPosition()` 是「自流启动起算」的累计值，而 `Seek` 只改我们的 `_baseTime`。
   实测 **Seek(10) 后声卡位置恒定偏 +3.01s**（正好是已播墙钟）→ `CheckAudioSync` 每 5 秒
   都看到假漂移 → 反复重定位 → 每次重定位丢弃并重开全部音频源（声音断续）+ 持锁阻塞视频线程（画面卡顿）。
   修法：按 `锚点渲染位置 +（声卡位置 − 锚点声卡位置）` 算，起播/Seek/Resume 重锚；
   漂移容差 0.15 → **0.30s**（声卡缓冲本身有 ~0.12s 固定延迟）+ 10s 冷却。

另外把 `Consumed.Wait(150)`（覆盖层 300）缩到 **5ms**：pump 是逐轨串行的，3 轨 + UI 忙时
一拍被拖到 450ms；防覆写的判断本来就在下一拍的 `!Consumed.IsSet → return`。

### 效果（同一台机器，8 秒窗口）

| 场景 | 修前 | 修后 |
|---|---|---|
| 1 轨 @800px 空闲 | 6 帧 / 0.8fps（卡死） | **139 帧 / 17.4fps** |
| 1 轨 @800px 加载 CPU | 1 帧 | **128 帧 / 16fps** |
| 2 轨 @640px 空闲 | 25 / 1 帧 | **136 / 95 帧** |
| 3 轨 @800px 空闲 | 3 帧 | **100 / 58 / 34 帧** |
| 3 轨 @800 + UI 卡 60ms + 加载 | 8/11/8 帧、1.2s 间隔 | 31/15/9 帧 |
| 边播边 seek（7 次） | 均值 370ms、1 次没恢复 | **均值 194ms、7/7 恢复** |
| seek 后声卡位置误差 | **+3.01s** | **−0.01s** |

### 遗留（已记录在 agents.md 约束 11）

- 本机上限：单轨 ~17fps、3 轨 @800px ~12fps（目标 24）。再往上要按轨并行解码或提高定时精度
  （`Thread.Sleep` 15.6ms 粒度拖着拍长），暂时靠编辑器预览画质自适应降分辨率换帧率。
- 极端负载（3 个 AboveNormal 忙线程 + 60ms UI 卡顿）下 3 轨会掉到 1~4fps、间隔 600ms
  —— 退化但**不再永久卡死**，负载过去会自己恢复。
- 音频 20ms 块：空闲均值 0.35ms、加载 1.35ms；加载下 8/600 块 >20ms（OS 调度，非代码问题）。
