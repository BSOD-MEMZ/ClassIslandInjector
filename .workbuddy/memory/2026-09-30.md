# 2026-09-30

## 真机反馈驱动的第二轮修复（用户：「模拟不准，真机还是卡 + 歌词对不上」）

用户报三件事：①真机仍然卡、**画面和唱的歌词对不上**；②改了导出画幅但舞台上没生效；
③播放预览时删光片段，seek 应该在 0s 且切停止，而不是在 0s 附近抽搐。

### 查清的两件"反直觉"的事（以后别再走弯路）

- **编辑器预览从来没启用硬解**（`Views/VideoEditorWindow.cs` 里没有任何 `HardwareDecoder` 赋值，
  而底图 `MainWindowStyleInjector` 与渲染 `VideoProjectRenderer` 都设了）。
  但**这台机器硬解没有收益**：auto 8.43ms / d3d11va 7.78ms / qsv 7.39ms vs 软解 **7.37ms/帧**
  —— 等于硬解没生效（或该流不支持），所以**没有接线**（避免白付设备初始化开销）。
- **降预览分辨率几乎不省 CPU**：320px 11.4ms、480px 10ms、640px 9.3ms、800px 12ms、1280px 13.1ms
  —— 成本在**解源码流**（1280×578 H.264），缩放到多小都差不多。所以「预览画质自适应」
  主要省的是 UI 侧的位图上传/合成，**不是解码**。这条推翻了之前"靠降分辨率换帧率"的假设。

### 修的 5 个问题（都进探针断言）

1. **节拍精度**：`Thread.Sleep` 默认 15.6ms 粒度 + 41.7ms 拍长 → 实际拍长 ~57ms。
   播放期间 `timeBeginPeriod(1)`（引用计数，停止恢复）+ 按截止时间睡 + 末段自旋 1ms。
   单轨 800px：**17.4fps → 23.1fps**（间隔 43ms）。
2. **追赶阈值改成按时间**（`MaxPictureLagSeconds = 0.15`，按源帧率换算帧数）：
   原来写死 8 帧对 54fps 源 = 允许落后 0.33s → 歌词必然对不上。
   并且 seek 追平后**本拍补一帧**（原来 seek 后直接 return，每跳少投一帧 → 画面一顿一顿）。
3. **改画幅不生效**：`ChangeCanvasSizeAsync` 判 `_stageBorder.Parent is Border`，
   而父级其实是 `stageInner`（**Grid**）→ 恒假 → `LayoutStage` 从未执行。改用 `_stageHost`。
4. **删光片段后抽搐**：`_duration == 0` 时每拍都「循环复位」把时钟拉回 0。
   播放器 `_duration <= 0` 直接退线程 + 时间归零；编辑器加 `SyncPreviewWithProject()`。
5. **播放中改倍速画面停住**（探针新发现）：0.5× 使目标帧号大幅倒退、帧游标停在高位 →
   `behind <= 0` 恒成立，实测停 6 秒。`behind < -2` 时重新 seek 对齐游标。

### 现状与遗留

单轨 @800px 23fps ✓；2 轨 @640 ~19/13fps；**3 轨 @800px ~15fps**（解码单线程串行，
54fps 源每轨 0.4 核，物理上做不完）。真正解决要么**按轨并行解码**、要么**预览用代理文件**。
用户当前工程：1920×1080、时间轴已清空。

## 第三轮：按轨并行解码 + 素材帧率才是真凶

用户反馈「单轨也严重丢帧丢音频」，并提了两个方向：用低分辨率试是不是我改坏了、然后按轨并行解码；
还问「用固定帧率的视频测试会不会更好」。

### 先回答帧率的问题：会，而且是决定性因素

用 `--makecfr` 合成 30fps CFR 素材与用户的手机视频（**1280×578 / 54.2fps VFR**）做对照：

| | 解一帧 | 每轨每秒解码量 | 1 轨 @800 | 3 轨 @800 |
|---|---|---|---|---|
| 手机视频 54.2fps | 7.37ms | 400ms/s | 21fps | 19.8/13.9/9.4 |
| 30fps CFR | 5.21ms | 156ms/s | **24fps** | **24/17.9/12** |
| **转码代理 800×368/30fps** | **1.87ms** | **45ms/s** | **24.3fps** | **24.1/18/12** |

（后两轨看着低只是因为它们在我的测试工程里起点是 2s/4s，按活跃时长算**都是 24fps**。）
⇒ **解码成本 = 源帧率 × 分辨率，与显示尺寸无关**；显示只要 24fps，54fps 素材白解 1.8 倍。

### 因此改了两处代码

1. **`VideoTranscoder` 输出帧率上限 30fps**（原来照抄源帧率）：按目标时间抽帧（顺序解码照读、
   ​跳过的帧不编码）。实测把用户的视频转成 800×368/30fps CFR、时长 16.466s（源 16.49s）✓。
2. **`VideoProjectPlayer` 按轨并行解码**：每轨一条 `TrackWorker`，主循环只打拍。
   - **异步派发**（不等收工）：第一版同步等 → 两次线程交接把单轨从 23fps 拖到 16.5fps。
   - 解码器的开关/seek/释放**只在本轨线程**，跨线程只用 Signal/Done/RestartPending 握手。
   - `Dispose` 不代释放：各轨线程退出前自释放（跨线程释放 native 上下文 = 静默崩溃老坑）。
   - 跳转用粘性 `RestartPending`，不会被随后的普通拍覆盖。

### 验证

- `RaceProbe`（解码中释放竞态）5 轮全过；`--audio`（渲染带音频）4 项 + 反向全过。
- `--stress` 用转码代理：**单轨/双轨/三轨全部 24fps**（间隔均值 42ms = 精确 1/24s）。
- 真机排查建议：让用户「重新导入素材并选压缩后导入」，或把已有素材重转一遍。

### 给用户的话

他原来的排查方向（低分辨率）经实测**没用**（320px 与 1280px 只差 2ms），
真正的原因是**素材帧率**——这一点他自己没想到，是这轮最有价值的发现。

## 第四轮：WebP 图片导致预览卡住 / 成片丢图（根因是 GDI+ 没有 WebP 解码器）

用户报「插入一张 webp 到视频编辑器，预览就在那几帧卡住」，并问是不是本来不支持 webp、
要不要阻断导入。

### 实测结论（不是「不支持 webp」，是「这条链路用的解码器不支持」）

- `OverlayFrameGenerator` / `VideoProjectRenderer` 走 **GDI+（System.Drawing）**，**GDI+ 没有 WebP
  解码器**（Windows 的「WebP 图像扩展」只注册 WIC 编解码器，GDI+ 不走 WIC）。
  实测 `new Bitmap(MemoryStream(bytes))` → `ArgumentException: Parameter is not valid.`；
  album.jpg / icon.png 正常。
- 插件里别的图片链路走 **Avalonia/Skia**，webp 全都正常：素材缩略图
  （`LoadAssetThumbnail` 里 `new Bitmap(stream)` 就在后台线程跑）、素材信息、主界面底图
  （`MainWindowStyleInjector.cs:3216`）→ 所以症状是「有的地方能看有的地方坏」。
- 日志实锤：`video-player.log` 里该片段期间状态恒为 `[覆盖层待发]`、「显N」帧号完全不涨。
- **连带更严重**：`VideoProjectRenderer` 拿不到 OverlayBuffer 就不合成 → **渲染成片里图片静默消失**。
- 用户草稿：`D:\Downloads\bg_5th.webp`（2.61MB / VP8L / 2048×1261），Kind=Image、Track=0、0~5s。
- 解码成本实测：Skia 解码 94ms + PNG 编码 868ms（一次性）。

### 改动（用户选「导入时自动转 PNG」+「无法解码时给提示」）

- `VideoTranscoder.IsGdiDecodable()`（探针）/ `NormalizeImage(path, cacheDirectory)`（GDI+ 解不了就用
  Avalonia `Bitmap(stream)` 解码、`Save` 成 PNG，落 `配置目录\image-cache\<名>-<源大小>.png`，可复用）。
- 导入素材（`ImportAssetsAsync`）与**打开工程**（新 `NormalizeProjectImagesAsync`，挂 `Opened`，
  后台线程）都改写图片引用 → 老工程里的 webp 也会被自动转掉。
- `WarnIfImageUndecodable()`：加片段 / 拖入 / 打开工程时若仍解不了，状态栏给明确提示（不再静默空白）。
- `OverlayFrameGenerator.GetCachedImage` catch 里每路径写一条日志（**不做负缓存**——用户明确
  不要，保留「文件被换掉能自愈」的行为，只是别每拍刷屏）。
- `agents.md` 新增「### 12. GDI+ 没有 WebP 解码器」。

## 第五轮：分离音频必崩 + 编辑器打开时主界面音频不停 + 清理噪音 label

用户报三件事（附了崩溃栈）：①点「分离音频」必崩 `ArgumentOutOfRangeException(index -1)`；
②剪视频时主界面底图「画面停了但声音还在」；③删掉「已框选 N 个片段」这类啰嗦 label。

### ① 崩溃根因：负索引

栈：`DetachAudioFromSelection → FillPropertyPanel → ShowSelectedClipFrame → _stageLayers[-1]`。

`DetachAudioFromSelection` 构造分离出的音频片段时落了 `Track = -1`（工程格式约定：音频片段的
`Track` **恒为 -1**，音频轨号在 `AudioTrack`）。而 `ShowSelectedClipFrame` 里的守卫写的是
**`clip.Track < _stageLayers.Count`** —— `-1 < Count` 恒成立（且 `_stageLayers` 此时可能是空的），
接着 `_stageLayers[-1]` 直接抛。**同类裸索引在文件里有 12 处**，只要片段 Track 是 -1 就有一半会崩。

修法（两层）：
- `VideoProject.Normalize`（读盘也走这里）把**所有音频片段的 Track 强制写回 -1**：
  历史数据里残留的脏值也一起清掉。
- 新增 `VideoEditorWindow.StageLayerOf(clip)`（判 `Track < 0 || >= Count` → null），
  把 12 处裸索引全换成它。**以后取画面片段的舞台层一律走这个 helper，不要再手写 `< Count`。**

### ② 编辑器打开时主界面还在放声音

`MainWindowStyleInjector.SuspendBackgroundPlayback` 只挂了 `_videoSource`（画面），
没管 `_videoAudio`（「播放声音」的输出）——**画面与音频是两条独立链，必须各挂一次**。
给 `VideoAudioPlayer` 加 `SetSuspended()`：挂起期间 `DecoderWaveProvider.Read` 吐静音但
**不推进解码器**（位置保留，恢复继续）。必须拦在 Read 里 —— WASAPI 的拉取是它主动发起的，
上层不调用挡不住。

### ③ 清理噪音 label（用户原话「让用户困扰且没有实际意义」）

- 删 `_audioHint` 整个控件 + `UpdateAudioHint(clip, audioCapable)` 方法
  （「该片段原声已静音」「音量为 0%」「所在音频轨已被静音」那一整块）。
- 删框选后往状态栏写的「已框选 N 个片段（可拖动移动 / Delete 删除）」——
  块本身已经高亮，这行是噪音。（框选功能本身不动，只不再写状态栏。）
- 删渲染对话框里那句「混入 N 个片段的声音（音量/淡入淡出/…与预览一致）」，
  以及配套的 `audioHint` 控件与局部函数（连它随 toggle 变化的逻辑一起）。

### 顺带

改写 `GetSelectedDisplayRect` 调用点后出现的 CS8604（`clip` 可能为 null）一并修掉 → 0 警告。

## 第六轮：触摸框选/拖素材、右键菜单、空轨道与「点不动」、素材残缺导致循环开头

### 触摸屏框选不出 / 素材拖不进轨道（关键 API 事实）

Avalonia 的 Fluent 主题把 `ScrollGestureRecognizer` 挂在 ScrollViewer **模板内部的
`PART_ContentPresenter`（ScrollContentPresenter）**上，**不在 ScrollViewer 自身**。
用 headless 探针实测确认：`scrollViewer.GestureRecognizers.Count == 0`，
而 `PART_ContentPresenter.GestureRecognizers.Count == 1`。
所以在 ScrollViewer 上找识别器是找不到的（我先写了一版错的，会静默无效）。
属性名是 `GestureRecognizers`（不是 `Gestures`，那是静态类）。`ScrollGestureRecognizer`
还有 `CanHorizontallyScroll` / `CanVerticallyScroll` 可关掉平移判定。

做法：`_lanesScroll` / `_timelineScroll` 各挂 `LayoutUpdated += DisableTouchPanOnce`
（挂 Loaded 太早，模板可能还没展开），一次性 `GetVisualDescendants().OfType<InputElement>()
.SelectMany(e => e.GestureRecognizers)` 里把 `ScrollGestureRecognizer` 两个方向置 false，
成功后立刻摘 handler。识别器失去平移能力后不再抢指针，触摸事件正常下发到泳道
（框选/拖拽自己处理）；滚轮与滚动条不受影响。

### 片段右键菜单

`BuildClipMenu(clip)` → `block.ContextFlyout`，`Opening` 时按当前选中重建：
复制 / 剪切 / 粘贴到播放头 / 在播放头分割 / 分离音频 / 静音 / 删除。
右键未选中的片段会先把它单选（已在多选里则保留多选，操作整组）。
新增 `CutSelectedClip()`（复制进剪贴板 + 移除 + 撤销 + 压缩轨道）。

### 渲染分辨率 & 轨道头按钮

- 预设改为 `360/480/640/800/1280/1600/1920/原尺寸`，默认选中 **800**（`SelectedIndex = 3`，
  三处 `?? "1280"` 同步改 `?? "800"`）。
- `TrackHeaderButton` Width 34 → **28**（3×28 + 2 spacing + 4 margin = 90 ≤ 92px 列宽），
  轨道头 Border 加 `ClipToBounds = true`。

### 删「预览播放中…」label（用户上次指的就是这个）

`StartPreview()` 与 `TogglePreview()` 里往 `_statusText` 写的「预览播放中…」改为不写
（播放/暂停状态由传输栏按钮图标表达）；`已暂停` 仍保留。
上一轮删的「已框选 N 个片段」是另一处，用户要的是这个。

### 「莫名其妙多一个空轨道」——真因找到

`CompactTracks()` 用 `_project.Clips.Select(c => c.Track)`，**把音频片段（Track = -1）
也算进去了**：`used` 含 -1 → `map[-1] = 0`，音频片段 Track 被写成 0（伪造的视频轨号），
视频轨 0 被顶到 1，`TrackCount`（只看非音频）随之 +1 → 凭空一条无片段的空泳道，
每「拖到轨道边界新建轨道」一次再涨一轨。

同一类错误还有三处搬移循环（`+1` 腾位）：
`HandleTimelineDrop` 插入新轨分支、`OnTimelinePointerReleased` 的组拖新建轨 / 落既有轨分支。
全部加 `if (c.IsAudio) continue;`（后两者同时跳过音频片段的 `FitsOnTrack`/`FitToTrack`）。
`CompactTracks` 改为只统计非音频片段，且音频片段不参与重映射。

### 「轨道点不动，resize 一下又好了」——真因找到

片段拖拽**刻意不做指针捕获**（窗口级驱动，规避不跟手），于是指针在**窗口外**松开时
`PointerReleased` 不达 → `_moveGroup` / `_trimState` / `_marqueeStart` 残留：
块一直浮在 `_timelineRoot` 上挡住泳道、泳道按下反复重新捕获框选起点。
**resize 触发 RefreshTimeline 从模型整体重建**，把这些残留视觉状态冲掉 → 所以「resize 就好了」。

兜底：窗口级 `PointerExited` / `Deactivated` → `CancelTimelineDrag()`；
`CancelTimelineDrag` 现在同时清 `_marqueeStart` / `_marqueeMoved` / `_marqueeRect`；
泳道另挂 `PointerCaptureLost` 清框选状态。

### 本地视频「一直循环开头那几秒」——是素材残缺，不是引擎 bug

样本 `D:\Downloads\什么时候告白啊!!!!!.40930379625.mp4`：
`--vdec` 显示「声明 217.666s @24fps（≈5224 帧），**只解出 30 帧**」；
`--loop` 显示复位完全正常（复位后首帧与起始首帧像素差 1.2）。
手工解 mp4 box：`ftyp` = `iso5/iso6/mp41/dash`，之后是 ~80 组 `moof`+`mdat`，
**末尾 moof 只有 728 字节**、无 `sidx`/`mfra` 索引 → 未下载完的 DASH/fMP4 分片流。
解 30 帧就 EOF，循环回开头再解同样 30 帧 = 用户看到的「一直循环开头几秒」。

`VideoFrameSource` 新增 `WarnIfFileTruncated()`：首次 EOF 对账「实际帧数 vs 声明时长×帧率」，
低于 30% 就写一条明确指向素材的告警日志（只报一次），避免误判成插件 bug。

## 第七轮（**推翻第六轮的结论**）：HEVC 只解出 30 帧的真因是解码循环写错；工具条 label 彻底移除

### 先认错：上一轮「素材残缺」的结论是错的

用户回：素材没坏，PotPlayer 一切正常（DXVA HEVC），可能是编码太新。查下来**用户是对的，我错了**。

`tools/AudioProbe --demux`（本轮新增的 demux 层探针）给出铁证：
```
nb_streams=2 duration=217.666s iformat=QuickTime / MOV
  stream[0] hevc 852x480 ... extradata=216B
  stream[1] aac
逐包读完：共 15416 个包
  stream[0] 包数=5220        ← 5220 个视频包，与声明的 5224 帧吻合
结束返回码 -541478725 = End of file（正常 EOF）
seek 到 100s 后解出 5 帧（✓ 中段数据可解）
```
文件完好、包都在、正常 EOF、中段解得动 → **问题在我们的解码器**。

### 真因：`avcodec_send_packet` 的 EAGAIN 被当成致命 EOF

`FFmpegVideoDecoder.ReadFrameLocked` 旧写法：喂一个包 → `receive_frame` 取**一帧**就 `return true`
（**从不排空**）→ `send_packet` 返回 `sr < 0` 就直接 `return false`。
`EAGAIN` 的真意是「输入队列满了，先取帧再回来喂」，被当成 EOF → 解码在开头几十帧处终止。
多线程解码的重排缓冲 + 从不排空，让 HEVC 很快撞上 EAGAIN。

**A/B 实测（worktree 构建旧版对照，`--vdec` 帧数）**：

| 素材 | 编码 | 修复前 | 修复后 |
|---|---|---|---|
| 什么时候告白（852×480） | **hevc** | **30** | **5220** |
| DECO_27（1920×1080） | h264 | 4379 | 4382 |
| 2026-07-20（2560×1440@120） | h264 | 1282 | 1282 |
| HAO_back（1920×1080） | h264 | 4349 | 4350 |

→ **HEVC 塌，H.264 正常**（H.264 那三个只多 1~3 帧，是 flush 排空延迟帧带来的正确性提升）。
所以症状像「某些视频坏了」，实为编码相关的触发条件。用户猜的「编码太新」方向是对的 ——
不是新到解不了，而是新到把我们的错误处理暴露出来。

**新写法**（`ReadFrameLocked` 重写为单循环 + `TryReceiveFrame`）：
① 先 receive（取到就返回）；② 取不到且已 flush → 真 EOF；③ 否则 `av_read_frame`，
非目标流必须 `av_packet_unref`（旧代码漏 unref，泄漏）；④ 读到尾先
`avcodec_send_packet(ctx, null)` **flush 一次**排空延迟帧并置 `_draining=true`；
⑤ `sr < 0` 只把**非 EAGAIN** 当错误。`_draining` 在 `RestartLocked`/`SeekToLocked` 复位。
附带修好「每个片段最后几帧被丢掉」（延迟帧以前从未取出）。

## 第八轮：修好「烂掉的」RaceProbe 并跑通（验证第七轮解码器改动无竞态回归）

用户问「tools/RaceProbe 已经烂了是什么意思」——先把事实查清：

- **是什么**：`tools\RaceProbe` 是「解码线程正在 `ReadFrame` 时另一线程 `Dispose`」的竞态回归探针
  （默认模式 5 轮；另有 `--info`/`--makecfr`/`--single`/`--stress`/`--audio`）。它守护的是
  `AccessViolationException(0xc0000005)` 静默击穿宿主进程那个坑。
- **怎么烂**：它靠 `<Compile Include>` 链接主项目源码编译。两个编译错误都在**被链接的文件**里，
  不是 RaceProbe 自己的代码：
  - `VideoTranscoder.cs:204` → `new Avalonia.Media.Imaging.Bitmap(stream)`（缺 Avalonia 包）
  - `OverlayFrameGenerator.cs:99` → `InjectorRuntime.ConfigDirectory`（缺主项目的静态门面）
- **何时烂**：`git log -S` 定位到提交 **`32f97ef`（修 WebP 静默丢图）** 同时引入了这两处。
  worktree 构建 `32f97ef^`（e928849）**RaceProbe 编译通过 0 错误**，到 `32f97ef` 就编译不过
  —— 铁证。而主项目编译**完全不受影响**（csproj 用 `DefaultItemExcludes` 排除 `tools\**`），
  所以没人发现。
- **修法（两处，很浅）**：
  - `RaceProbe.csproj` 加 `<PackageReference Include="Avalonia" Version="11.3.6" />`
    （只是让 `VideoTranscoder.cs` 编译过；探针运行路径不碰那段 Bitmap 代码 = 素材导入才走的，
    所以不需要注册渲染平台）。
  - `Program.cs` 加 `InjectorRuntime` 桩（照抄该文件已有的 `DiagnosticLog`/`FFmpegRuntime` 桩写法），
    `ConfigDirectory` 给临时目录，绝不碰宿主配置。
- **验证**：HEVC 素材跑默认竞态模式 **5/5 通过**（Dispose 阻塞 ~109ms、期间读帧 112~125、
  读线程无异常、已退出、释放后再读返回 false），退出码 0；`--info` 也正常。
  → 结论：**第七轮的解码器重写没有引入竞态回归**（锁纪律没变，`_draining` 只在 `_gate` 内访问）。
- 已在 `agents.md` 的 tools 清单里写明「改了被链接的文件后要顺手构建一下 RaceProbe」这条教训。
